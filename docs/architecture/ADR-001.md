# ADR-001: Выбор архитектуры для Workout Tracker

## Контекст

Проект — мобильное приложение для трекинга тренировок (аналог Hevy, Strong). Ключевые характеристики контекста:

| Фактор | Значение |
|--------|----------|
| Команда | 5–8 разработчиков |
| Time-to-Market | MVP за 2–3 месяца |
| Нагрузка | 10K пользователей на старте, рост до 100K+ |
| SLA | 99.9% uptime (не финансовая система) |
| Бюджет | Ограниченный, облачный стек |
| Offline-first | Критично: запись тренировок без сети |
| Платформы | Android (Kotlin), iOS (Swift) |

### Проблемы существующих решений (из анализа TrainHeroic)

1. Потеря данных при завершении тренировки (нет атомарной фиксации)
2. Сброс данных при сворачивании приложения (состояние в памяти)
3. Потеря данных при смене сети (нет персистентности)
4. Вечный таймер (fire-and-forget без ACK)
5. Пропуск тапов (синхронный I/O в UI-потоке)

## Рассмотренные альтернативы

### Вариант 1: Монолит

**Описание:** Единое серверное приложение + мобильные клиенты.

**Плюсы:**
- Быстрый старт, один pipeline деплоя
- Локальные ACID-транзакции
- Простое тестирование

**Минусы:**
- Масштабирование только целиком
- Сложность добавления новых платформ
- Риск превращения в «ком грязи» при росте

### Вариант 2: Модульный монолит ✅

**Описание:** Один серверный артефакт с чёткими границами модулей (bounded contexts): Users, Workouts, Exercises, Programs, Sync. Мобильный клиент с локальной БД и фоновой синхронизацией.

**Плюсы:**
- Быстрый старт (TTM недели)
- Границы модулей подготовлены для будущей декомпозиции
- ACID-транзакции внутри модулей
- Простой деплой и мониторинг
- Модуль выделяется в микросервис с минимальным переписыванием

**Минусы:**
- Масштабирование целиком (не критично на старте)
- Требует дисциплины в соблюдении границ

### Вариант 3: Микросервисы

**Описание:** Независимые сервисы на каждый bounded context.

**Плюсы:**
- Независимое масштабирование
- Независимые релизы

**Минусы:**
- Высокая ops-сложность (K8s, service mesh, tracing)
- Распределённые транзакции (Saga, компенсации)
- Медленный старт (инфраструктура с первого дня)
- Избыточно для команды < 10 человек

## Решение

**Выбран Вариант 2: Модульный монолит**

### Обоснование по критериям

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| Time-to-Market | ★★★★★ | Один артефакт, один pipeline, быстрый старт |
| Scalability | ★★★☆☆ | Масштабирование целиком, достаточно до 100K+ пользователей |
| Reliability | ★★★★☆ | Локальные транзакции, изоляция отказов на уровне модулей |
| Cost | ★★★★★ | Минимальная инфраструктура, один сервер |
| Maintainability | ★★★★☆ | Чёткие границы модулей, архитектурные тесты в CI/CD |

### Архитектурные принципы

1. **Bounded Contexts:** Users, Workouts, Exercises, Programs, Sync — чёткие границы, контракты вместо прямых вызовов
2. **Offline-first клиент:** Локальная БД (Room/SQLite) как источник правды, фоновая синхронизация через Outbox-очередь
3. **Идемпотентность:** Все операции записи идемпотентны (Idempotency-Key)
4. **Архитектурные тесты:** ArchUnit/NetArchTest фиксируют правила зависимостей в CI/CD
5. **Путь к микросервисам:** Модуль выделяется в сервис с минимальным переписыванием при необходимости

## Последствия

### Положительные
- Быстрый запуск MVP (2–3 месяца)
- Простая эксплуатация (один сервер, один мониторинг)
- Подготовлена декомпозиция для будущего роста

### Отрицательные
- Масштабирование только целиком
- Риск нарушения границ модулей без архитектурных тестов
- Единая точка отказа (митируется репликацией)

### Риски и митигация

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Нарушение границ модулей | Средняя | ArchUnit тесты в CI/CD |
| Рост нагрузки сверх ожидаемой | Низкая | План миграции на микросервисы (Strangler Fig) |
| Сложность offline-first синхронизации | Средняя | Идемпотентность, Outbox-очередь, компенсации |
